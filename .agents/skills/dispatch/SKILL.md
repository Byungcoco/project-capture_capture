# Dispatch

## Overview

계획 하나를 받아 서브에이전트에게 태스크 단위로 실행시키는 **조정 스킬**이다. 조정자는 구현하지 않고 계획 검증, 태스크 분해, 디스패치, 검수, 통합만 담당한다.

**핵심 원칙:** 조정자는 코드를 쓰지 않는다. 구현 태스크는 RED 증거 없이 완료로 인정하지 않는다.

이 스킬은 superpowers와 gstack 스킬을 **조합**한다. 대체하지 않는다. 각 단계에서 해당 스킬을 실제로 읽고 따른다.

## When to Use

- 실행할 계획이 이미 있다 (`superpowers:writing-plans`, `claude-mem:make-plan`, 또는 사용자가 직접 준 계획)
- 태스크가 2개 이상이고 대체로 독립적이다
- 컨텍스트를 아끼면서 여러 태스크를 돌리고 싶다

**쓰지 않을 때:**
- 계획이 없다 → `superpowers:brainstorming` 후 `superpowers:writing-plans`
- 태스크 하나짜리 작업 → 직접 구현 (단, TDD는 그대로 적용)
- 태스크들이 서로 강하게 얽혀 있다 → 직접 순차 구현
- 버그 원인을 아직 모른다 → `superpowers:systematic-debugging`

## 런타임 매핑

세 런타임에서 동일하게 동작해야 한다. 동작 이름은 같고 도구만 다르다.

| 동작 | Claude Code | Codex | Antigravity (`agy`) |
|---|---|---|---|
| 서브에이전트 디스패치 | `Agent` (`subagent_type: general-purpose`) | `spawn_agent` / `wait_agent` / `close_agent` | `invoke_subagent` (`TypeName: self`=구현, `research`=읽기 전용) |
| 병렬 디스패치 | 한 응답에 `Agent` 여러 번 | `spawn_agent` 여러 번 후 `wait_agent` | `invoke_subagent` 여러 번 |
| 진행 추적 | `TaskCreate`/`TaskUpdate` | 없음 | task artifact (`write_to_file`, `IsArtifact: true`, `ArtifactType: "task"`) |
| 스킬 읽기 | `Skill` 도구 또는 `/이름` | 스킬 파일을 직접 Read | 스킬 파일을 직접 Read |

**전제 조건:** Codex는 `~/.codex/config.toml`에 `[features] multi_agent = true`가 필요하다. 없으면 디스패치 불가 — 사용자에게 알리고 직접 순차 실행으로 전환한다.

**진행 상태의 원본은 항상 원장 파일이다.** todo 도구와 task artifact는 런타임마다 있거나 없고 컴팩션에서 사라진다. 원장은 남는다.

## 절차

### 0. 준비

1. 계획 파일 경로를 확정한다. 없으면 여기서 멈추고 계획부터 만든다.
2. 작업 공간을 만든다: `.dispatch/<계획파일 basename>/` (git-ignored). 여기에 원장, 브리프, 보고서, 리뷰 패키지를 둔다. 다른 계획의 디렉터리는 읽지도 쓰지도 않는다.
3. 원장 `.dispatch/<basename>/progress.md`를 확인한다. 첫 줄이 이 계획 파일을 가리키고 `Task <N>: complete`가 있으면 그 태스크는 **끝난 것이다. 다시 디스패치하지 않는다.** 첫 줄이 다른 계획을 가리키면 건드리지 말고 새로 만든다.
4. 원장 첫 줄: `# dispatch ledger — plan: <계획 파일 경로>`
5. main/master에서 바로 시작하지 않는다. `superpowers:using-git-worktrees`로 격리하거나 브랜치를 만든다.

### 1. 계획 검증

디스패치 전에 계획을 한 번 검증한다. **`gstack:plan-eng-review`**를 사용한다 — 아키텍처, 데이터 흐름, 엣지 케이스, 테스트 커버리지를 훑는다. 범위 자체가 의심스러우면 `gstack:plan-ceo-review`를 먼저 돌린다.

동시에 계획을 직접 한 번 읽고 다음 충돌을 찾는다.

- 태스크끼리, 또는 태스크와 전역 제약이 모순되는 곳
- 계획이 요구하지만 리뷰 기준으로는 결함인 것 (아무것도 단언하지 않는 테스트, 의도적 코드 중복)
- **테스트할 수 없게 쓰인 태스크** — 관측 가능한 동작이 명시되지 않은 태스크

찾은 것은 **한 번에 묶어서** 사용자에게 묻는다. 태스크마다 끊어 묻지 않는다. 깨끗하면 말없이 진행한다.

### 2. 분해와 모드 결정

태스크당 하나씩 todo(또는 task artifact)를 만들고, 실행 모드를 정한다.

| 상황 | 모드 | 따를 스킬 |
|---|---|---|
| 같은 파일군을 건드리는 순차 태스크 | 직렬 1개씩 | `superpowers:subagent-driven-development` |
| 공유 상태 없는 독립 태스크 | 병렬 | `superpowers:dispatching-parallel-agents` |
| 계획을 다른 세션으로 넘김 | 세션 분리 | `superpowers:executing-plans` |

**구현 서브에이전트를 병렬로 돌리는 것은 서로 다른 파일군을 건드릴 때만이다.** 겹치면 충돌한다. 애매하면 직렬이 정답이다.

**모델 선택:** 디스패치할 때 모델을 항상 명시한다. 생략하면 세션 모델(대개 가장 비싼 것)을 상속한다. 계획에 코드가 그대로 있는 전사 작업은 싼 모델, 여러 파일 통합은 표준, 설계 판단과 최종 전체 리뷰는 가장 강한 모델.

### 3. 디스패치 — TDD 게이트

각 태스크마다 `task-brief.md` 템플릿으로 브리프 파일을 쓴다. **브리프의 `## RED 명세` 슬롯은 조정자가 채운다.** 빈칸으로 디스패치하지 않는다.

디스패치 프롬프트에 넣을 것은 다섯 가지뿐이다.

1. 이 태스크가 프로젝트에서 어디에 놓이는지 한 줄
2. 브리프 파일 경로 — "먼저 읽어라, 이게 네 요구사항이고 값은 그대로 쓴다"
3. 이전 태스크가 만든 인터페이스·결정 중 브리프가 알 수 없는 것
4. 브리프에서 네가 발견한 모호함에 대한 조정자의 판단
5. 보고서 파일 경로와 보고 계약

**세션 히스토리를 붙여넣지 않는다.** "Task 1~3 이후 상태" 같은 누적 요약은 넣지 않는다. 정확한 값(숫자, 문자열, 시그니처, 테스트 케이스)은 브리프에만 있다. 계획 파일 전체를 읽히지 않는다.

**조정자가 확인하지 못한 값은 추정해서 채우지 않는다.** 소스를 못 읽었으면 `미확인: <구현자가 소스에서 확정할 것>`으로 표시하고, 브리프에 "실제 코드와 다르면 맞춰서 지어내지 말고 멈추고 보고하라"를 함께 넣는다. 그럴듯한 시그니처를 채워 넣은 브리프는 구현자가 그것을 사실로 믿기 때문에 빈칸보다 나쁘다.

디스패치 전 `git rev-parse HEAD`로 BASE를 기록한다. 리뷰 패키지에 필요하다.

### 4. 태스크 검수

보고서를 받으면 **먼저 슬롯부터 확인한다.**

```
RED 증거 비었거나 "테스트 작성함" 같은 서술뿐  → 반려. 재디스패치.
GREEN 증거 비었음                              → 반려. 재디스패치.
```

증거는 **실행 출력 원문**이어야 한다. 요약이나 주장은 증거가 아니다. 이 확인을 통과해야 리뷰로 넘어간다.

그다음 리뷰를 돌린다. 두 가지 판정을 모두 받아야 한다 — **명세 준수**와 **코드 품질**. `superpowers:requesting-code-review`의 리뷰어 템플릿을 쓰고, diff는 파일로 넘긴다(BASE..HEAD 전체 범위. `HEAD~1`은 다중 커밋 태스크를 잘라먹는다).

리뷰어에게 **결론을 미리 주지 않는다.** "이건 플래그하지 마", "이건 Minor로 처리해" 같은 문장을 쓰고 있다면 멈춰라 — 리뷰 루프를 아끼려고 판정을 선점하는 중이다.

Critical/Important는 수정 루프로. Minor는 원장에 적고 최종 리뷰로 넘긴다. 계획 텍스트와 충돌하는 지적은 조정자가 판단하지 않는다 — 지적과 계획 텍스트를 나란히 놓고 사용자에게 어느 쪽이 우선인지 묻는다.

태스크가 끝나면 원장에 `Task <N>: complete — <커밋 SHA들>`을 추가한다.

### 5. 통합 검증

모든 태스크가 끝나면 한 번만 한다.

1. **전체 브랜치 리뷰** — `superpowers:requesting-code-review`, 가장 강한 모델. 원장의 Minor 목록을 함께 넘겨 머지 전 처리할 것을 골라내게 한다.
2. **구조 리뷰** — `gstack:review`로 base 브랜치 대비 diff를 본다. 신뢰 경계를 지나는 변경이 있으면 `/security-review`도 돌린다.
3. **웹 동작이 바뀌었다면** — `gstack:qa`로 실제 브라우저에서 확인한다. 유닛 테스트 통과는 화면이 동작한다는 증거가 아니다.
4. 전체 테스트, 타입 검사, 프로덕션 빌드를 실행하고 **출력을 남긴다.**

### 6. 마무리

`superpowers:finishing-a-development-branch`로 통합 방식을 정한다. PR까지 한 번에 가려면 `gstack:ship`.

이 저장소에서는 마무리 전에 AGENTS.md의 위키 동기화 절차(`tools/wiki_sync.py finalize`)를 실행한다.

## TDD 게이트

**구현 태스크는 실패를 관측한 테스트 없이 완료되지 않는다.** 조정자든 서브에이전트든 같다.

게이트는 브리프와 보고서의 **필수 슬롯**으로 강제한다. 규칙을 문장으로 적어두는 것으로는 새지 않게 막을 수 없다.

| 슬롯 | 채우는 주체 | 비면 |
|---|---|---|
| 브리프 `## RED 명세` | 조정자 | 디스패치 불가 |
| 보고서 `## RED 증거` | 구현자 | 보고 반려 |
| 보고서 `## GREEN 증거` | 구현자 | 보고 반려 |
| 보고서 `## 보안 검토` | 구현자 | 보고 반려 |

`## 보안 검토`는 대상이 없어도 `해당 없음 — <이유>`로 채운다. 신뢰 경계를 지나는 태스크라면 방어를 설명하는 문장이 아니라 **거부 케이스 테스트**가 들어 있어야 한다. 취약점을 발견했는데 이번 범위에서 완화하지 못했다면 그 태스크는 `DONE`이 아니라 `BLOCKED`다 — "다음 스프린트 권장"을 달아 통과시키지 않는다. 기준은 AGENTS.md의 `보안 검토 기준`이다.

### 커밋을 두 개로 나눈다

디스패치 프롬프트에 명시한다: **테스트만 담은 커밋을 먼저 만들고, 구현 커밋을 그 위에 따로 쌓는다.**

```
<sha1> test: add failing tests for refund limit    ← 이 시점에 구현이 없다
<sha2> feat: enforce refund limit in validate()
```

붙여넣은 출력은 사후에 만들어낼 수 있지만 **커밋 순서는 만들어낼 수 없다.** 조정자는 `git show <sha1>:<구현파일>`로 그 시점에 구현이 없었음을 직접 확인한다. 붙여넣기를 신뢰할 필요가 없어진다.

이걸 지키면 RED 증거는 부수적으로 따라온다. 지키지 않은 보고는 슬롯이 채워져 있어도 순서를 증명하지 못한다.

**산출물이 실행 코드가 아닌 태스크**(문서, 위키, 에셋 변환, 순수 설정값)는 `## RED 명세`에 `N/A: <비코드 산출물 종류>`를 명시하고, 브리프 `## 검증` 슬롯에 **실행 가능한 확인 명령**을 넣는다. 조정자가 판단해서 빈칸으로 두는 경우는 없다 — 둘 중 하나는 반드시 찬다.

상세 사이클은 `superpowers:test-driven-development`가 원본이다.

### RED 증거가 없는 보고서를 받았을 때

구현자를 재개해서 증거만 받아온다. 수정 루프 1~3라운드와 같은 동작이며, 태스크 전체를 다시 시키는 것이 아니다.

**다음 세 가지는 게이트를 통과시키지 않는다.**

**조정자가 직접 테스트를 돌려 통과를 확인하는 것.** 그건 GREEN을 확인한 것이지 RED가 아니다. 테스트가 지금 초록이라는 사실은 그 테스트가 구현 전에 쓰였는지에 대해 아무것도 말해주지 않는다. **구현 후에 쓴 테스트는 언제나 즉시 통과한다** — 그래서 통과는 증거가 되지 못한다. 조정자가 대신 확인해 주면 게이트는 그 자리에서 사라지고, 다음 태스크부터 구현자는 슬롯을 비워도 된다는 것을 학습한다.

**구현을 stash하거나 이전 커밋으로 되돌려 실패를 재현하게 시키는 것.** 사후 재현은 순서를 되돌리지 못한다. 그 테스트가 완성된 코드를 보고 쓰였다는 사실은 그대로다. 코드를 보고 쓴 테스트는 **코드가 하는 일**을 검증한다. 테스트가 검증해야 하는 것은 **코드가 해야 할 일**이다. 둘은 겹쳐 보이지만, 구현자가 잊은 케이스에서 정확히 갈라진다.

**"이미 늦었으니 GREEN이라도 받는" 것.** 게이트에 반쪽 경로는 없다.

구현자가 테스트를 먼저 쓰지 않았다면 그 태스크의 테스트는 신뢰할 수 없다. 브리프의 `## RED 명세`를 주고 **테스트를 지운 뒤 명세로부터 새로 쓰게** 하고, 구현을 되돌린 상태에서 실패를 관측하고 다시 구현하게 한다. 비싸다.

그래서 게이트의 자리는 보고 시점이 아니라 **디스패치 시점**이다. `## RED 명세`를 채워서 내보내면 이 상황 자체가 생기지 않는다. 이 비용을 한 번 치렀다면, 고칠 것은 그 태스크가 아니라 당신의 디스패치 습관이다.

## 합리화 표

| 변명 | 실제 |
|---|---|
| "계획에 테스트가 안 적혀 있다" | 계획의 결함이다. RED 명세를 조정자가 쓰거나 사용자에게 묻는다. 게이트를 여는 이유가 아니다. |
| "서브에이전트가 테스트했다고 했다" | 주장은 증거가 아니다. 실패 출력 원문이 없으면 반려다. |
| "내가 직접 `npm test`를 돌려 통과를 확인했다" | GREEN을 확인한 것이다. 그 테스트가 구현 전에 쓰였는지는 여전히 모른다. 나중에 쓴 테스트는 언제나 즉시 통과한다. |
| "직접 확인 가능한 걸 왜 재디스패치로 돌리나" | 확인 가능한 것은 GREEN뿐이다. RED는 조정자가 사후에 만들어낼 수 없는 정보다. |
| "구현을 stash하고 돌리면 RED를 재현할 수 있다" | 사후 재현은 순서를 되돌리지 못한다. 코드를 보고 쓴 테스트는 코드가 하는 일을 검증한다. |
| "이미 늦었으니 최소 GREEN이라도 받자" | 게이트에 반쪽 경로는 없다. |
| "로그를 안 붙였을 뿐 거짓말은 아닐 것이다" | 게이트는 거짓말을 잡는 장치가 아니라 순서를 기록하는 장치다. 선의여도 증거는 필요하다. |
| "재디스패치는 과잉 대응이다" | 전체 재작업과 증거 보완은 다르다. 구현자를 재개해 증거만 받는다. |
| "출력 붙여넣기가 컨텍스트를 먹는다" | 그래서 보고서를 파일로 쓰게 한다. 증거를 없애는 게 아니라 파일에 둔다. |
| "리팩터링이라 동작이 안 바뀐다" | 동작이 안 바뀌면 기존 테스트가 그대로 통과해야 한다. 그 통과 출력이 증거다. |
| "태스크가 너무 작다" | 작은 태스크의 테스트는 30초다. |
| "병렬로 돌려야 빠르다" | 같은 파일을 건드리는 병렬은 충돌 복구로 더 느리다. |
| "리뷰까지 돌리면 오래 걸린다" | 검수 없는 디스패치는 조정자가 나중에 전부 다시 읽는다는 뜻이다. |
| "내가 직접 하는 게 빠르겠다" | 그래도 된다. 단 TDD는 그대로 적용된다. |

## Red Flags — 멈추고 다시

- 브리프의 RED 명세를 비운 채 디스패치했다
- 보고서의 RED 증거가 출력이 아니라 "테스트를 작성하고 실행했습니다" 같은 서술이다
- RED 증거가 없어서 **조정자가 직접 테스트를 돌렸다**
- 구현자에게 "stash하고 RED를 재현하라"고 시켰다
- "최소 GREEN이라도"라고 쓰고 있다
- 디스패치 프롬프트에 이전 태스크 요약을 붙여넣고 있다
- 리뷰어 프롬프트에 "이건 플래그하지 마"라고 쓰고 있다
- 원장 없이 todo만으로 진행 중이다
- 조정자가 직접 구현 코드를 쓰고 있다
- 같은 파일군 태스크를 병렬로 디스패치했다

## 흔한 실수

**계획 전체를 서브에이전트에게 읽힌다** → 브리프 파일만 준다. 태스크 하나의 요구사항만 들어 있어야 한다.

**`HEAD~1`을 BASE로 쓴다** → 다중 커밋 태스크의 앞 커밋들이 리뷰에서 사라진다. 디스패치 직전에 기록한 SHA를 쓴다.

**컴팩션 후 완료된 태스크를 다시 디스패치한다** → 원장과 `git log`를 믿는다. 기억을 믿지 않는다.

**병렬 결과를 개별로만 확인한다** → 각각 통과해도 합치면 깨진다. 통합 후 전체 테스트를 다시 돌린다.
